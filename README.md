# Bingo

An offline 90-ball bingo application for community events, with a private operator view and a separate public display. Development starts on macOS with one Electron + TypeScript codebase; Windows support is planned for later.

## Current status

This repository contains a **desktop feasibility prototype, not a playable bingo game**. It opens operator and public windows, can play a bundled local video, and persists one current 90-ball event in a SQLite database under Electron's user-data directory (`current-event.sqlite`). Startup loads that event or explicitly creates it when absent. Invalid or unreadable data causes a visible startup error, not a reset. The operator window displays and reloads the persisted current event, its ordered called numbers, and the remaining count. It supports manual draws (integer 1–90) and digital draws; the visible history changes only after a successful persisted acknowledgement. Failed requests retain the last acknowledged history, warn that it may be stale, and offer reload. The public window shows the persisted ordered calls and latest draw read-only, receiving post-commit updates through a fixed receive-only sandbox preload. Opening or reopening it loads the current persisted event. Tickets and claims are not implemented. Three generated themes are registered from shared components: jules (default), light, and high-contrast; see [docs/design-system.md](docs/design-system.md). The theme selector in the operator's **Configuración** tab saves one allow-listed theme id alongside the current event in `current-event.sqlite` (schema v3 adds a `theme` column with a migration from earlier versions); both windows switch only after that save commits, a failed save keeps the last committed theme, and the public window receives the theme read-only on open and on every change. Pages stay hidden until a theme is applied. If the committed theme has not reached the public window within two seconds, it reveals the default jules theme and switches as soon as the committed theme arrives. An unreadable theme value falls back to jules without being overwritten. The storage layer keeps multiple events and one active event pointer (`events`, `active_event` tables, schema v4; schema v5 retires the `pixel-classic` theme id, migrating stored values to `jules` in one transaction and rejecting unknown values); creating, listing, and selecting events is implemented at the storage level only, with no UI yet. Each event can store Línea and Bingo prizes (whole euros from 0 to 100 000, where 0 means no money, plus an optional lot of up to 120 characters) in an `event_prizes` table added by the schema v6 migration; operator-only `prizes:get`/`prizes:update` IPC validates them and publishes committed prizes to the public window over the receive-only `publicEventPrizes` channel. **Configuración** edits the active event's name, date, place, and theme as a draft. The draft is previewed only in a 16:9 simulator: the bundled public page, framed without any preload and fed the committed history. **Guardar cambios** commits it. Leaving the tab or selecting another event with unsaved edits offers Save, Discard, or Cancel. The operator window is a Spanish, full-viewport desktop application (`bingo-app-shell`): a header with the three tabs (**Eventos**, **Configuración**, **Bingo**) and the active event, the tab workspace, and a status bar with the game phase and event state. The document never scrolls; long lists and forms scroll inside their own panel. **Bingo** is dominated by the operator's 1–90 board (`bingo-operator-board`: ten numbers per row, uncalled / called / latest / disabled states, arrow-key navigation). In **Manual** draw mode, clicking or pressing Enter on an uncalled number calls it through the same validated manual-draw IPC; the board only ever shows committed calls, marks the request in flight, and flags a possibly stale history. In **Digital** mode the board is read-only and the rail's **Sacar bola** draws. A side rail (`bingo-side-rail`) holds the last call with a strip of the last eight calls, the draw mode and controls, the Línea / Bingo / Sorteo de empate claim buttons (disabled until claims exist), and the public-window controls. Operator forms (**Eventos** › Nuevo evento and both **Configuración** panels) are built from shared, form-associated Lit controls: `bingo-text-field`, `bingo-date-field` and `bingo-select-field` (label, hint, an announced error with an icon, required/disabled/pending states, `aria-describedby` wiring) and `bingo-form-actions` (status, secondary, then primary action, optionally sticky), with `bingo-button` gaining `type="submit"`, a primary variant, and a `block` variant that stretches to its container. `tests/components/form-components.test.mjs` covers every control state in both themes until Storybook exists.

## Run the prototype

Requires Node.js 24 and npm on macOS. From the repository root:

```sh
npm ci
npm test
npm start
```

`npm start` builds the TypeScript main process and preloads as CommonJS in `dist/`, bundles both Lit/Vite renderer pages and local assets into `dist/renderer/`, then opens the operator window. Draw manually by picking a number on the board (or typing 1–90), or switch to digital mode and draw; use **Recargar evento** to fetch the persisted event after an error. Use **Abrir pantalla pública** to show the read-only public event display. Closing and reopening loads persisted history again. On a Mac with a second screen it opens fullscreen there; with one screen it opens as a preview. A separate feasibility/media section contains a one-second sample video with manual playback controls; it is not event state. `npm run build` generates the three Style Dictionary/DTCG theme stylesheets in ignored `src/generated/` before Vite bundles both pages; it does not require committed generated CSS. `npm run build:tokens` regenerates just the tokens and `npm run test:tokens` checks the reference/semantic contracts, including WCAG contrast pairs per theme. Token architecture, naming rules, themes and the component catalog are documented in [docs/design-system.md](docs/design-system.md). `npm run gallery` opens a development-only component and theme state gallery on the Vite dev server; it is excluded from `npm run build`. The jules theme's Roboto Mono Variable font is bundled from `@fontsource-variable/roboto-mono` (OFL-1.1) and never fetched at runtime. `npm run test:build` validates the generated pages, offline resources, themes, and sibling preloads after a build. `npm test` runs source tests without requiring `dist/`. `npm run test:smoke` launches the built app with Playwright's Electron support and checks startup on an isolated profile, the three operator tabs, no document scroll on any tab at 1280×720 and 1920×1080, a committed draw reaching the public window, the Configuración draft preview and Save/Discard/Cancel guard, event creation and selection, theme/event/history persistence across a restart, and the receive-only public boundary. It rebuilds first when `dist/` is missing or older than its sources, and on Linux without a display re-runs itself under `xvfb-run -a`. Every launch uses a fresh `bingo-smoke-*` `--user-data-dir` in the OS temp directory; the script refuses any other profile, checks that Electron actually uses it and that the real profile's database is untouched, and always deletes it. On failure it writes window screenshots and a main-process/console log to `$SMOKE_ARTIFACTS_DIR` (default `verification/artifacts/electron-smoke/`, git-ignored). An isolated Electron 41/macOS smoke confirmed both built `file://` pages, Lit/CSP loading, local MP4 readiness, manual and digital updates, public close/reopen, and app relaunch recovery. Packaged builds are covered by [macOS packaging](docs/macos-packaging.md) and [Windows packaging](docs/windows-packaging.md). Persistence uses built-in `node:sqlite` (`DatabaseSync`), which requires the bundled Electron/Node runtime to support this experimental API; host Node tests alone do not validate Electron startup or quit/reopen recovery.

## Continuous integration

GitHub Actions runs one Ubuntu job on every pull request (whatever its base branch, so stacked PRs are checked too) and on pushes to `main`. It uses Node.js 24, `npm ci`, and these checks in order:

```sh
npm test
npm run test:tokens
npm run build
npm run test:build
npm run test:components
xvfb-run -a npm run test:smoke
```

The runner installs Chromium's Linux system dependencies with `npx playwright install-deps chromium`; `npm run test:components` installs Chromium itself before running Web Test Runner. Before the checks it makes Electron's `chrome-sandbox` helper setuid root, so the smoke runs with the Chromium sandbox enabled on Ubuntu. The smoke step has a five-minute limit; when it fails, its screenshots and log are uploaded as the `electron-smoke` workflow artifact. The single job keeps token-generated CSS and build artifacts sequential. To reproduce the checks locally, use Node.js 24, run `npm ci`, provision Playwright's Chromium system dependencies on Linux, then run the commands above in order. CI tests source, token contracts, built artifacts, browser components, and one Electron launch on Linux; it does not package the application or validate macOS or Windows runtime/packaging. Hosted CI results require a published branch or PR; required-check branch protection is not configured here.

## macOS package

A separate `macOS package` workflow builds an unsigned (ad-hoc signed) `Bingo.app`, dmg and zip for arm64 and x64 on `macos-15`, verifies the ad-hoc signature, and smokes the packaged app against a temporary `--user-data-dir`. On macOS, `npm run package:mac` writes the build to ignored `release/`; `npm run test:package` runs the packaged-app smoke. See [docs/macos-packaging.md](docs/macos-packaging.md) for the packaged user-data location and upgrade behaviour, the manual release check, and the signing and notarization procedure with its required secrets.

## Windows package

A separate `Windows package` workflow builds unsigned per-user NSIS installers on `windows-latest`, then installs, upgrades, relaunches and uninstalls the packaged app against a temporary `--user-data-dir`. On Windows, `npm run package:win` writes the installer to ignored `release/windows/`. See [docs/windows-packaging.md](docs/windows-packaging.md) for what is verified, platform differences, and what remains unverified.
